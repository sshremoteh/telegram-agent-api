# Задание для Google Antigravity: создать и запустить Local Telegram Agent API

> **Цель:** самостоятельно создать в текущем рабочем пространстве полноценный локальный проект для Ubuntu/Linux, который позволяет ИИ-агентам взаимодействовать с обычным пользовательским Telegram-аккаунтом через REST API и MCP.
>
> **Главное требование:** не ограничивайся инструкциями и примерами. Создай все файлы проекта, установи зависимости, выполни настройку и проверки, запусти сервис и подключи MCP к Antigravity настолько, насколько позволяет текущая среда. Не заявляй об успешном запуске, если не проверил это командами.

## 1. Правила работы

1. Сначала проверь ОС, Python, доступность `systemd --user`, текущее рабочее пространство и доступные настройки MCP Antigravity.
2. Работай только в каталоге проекта `telegram-agent-api` внутри текущего рабочего пространства либо в каталоге, который пользователь явно указал.
3. Не перезаписывай существующие файлы без изучения их содержимого и резервной копии.
4. Не запрашивай и не печатай в логах API Hash, API-токен, код входа, пароль 2FA, содержимое `.env` или Telegram session.
5. Не пытайся обходить CAPTCHA, ограничения Telegram, лимиты частоты или средства безопасности.
6. Не отправляй сообщения другим пользователям и не выполняй необратимые действия без явного подтверждения пользователя. Для первичной проверки используй только `get_me`, `get_dialogs` и другие операции чтения. Не отправляй тестовое сообщение, пока пользователь явно не указал тестовый чат и не подтвердил отправку.
7. Не публикуй REST API в интернет. Слушать только `127.0.0.1`.
8. Если для входа в Telegram нужны номер, код подтверждения или пароль 2FA, остановись на интерактивном локальном шаге и попроси пользователя ввести их самому в терминале. Не проси присылать секреты в чат с ИИ.
9. Если Antigravity не позволяет автоматически изменять конфигурацию MCP, создай готовый конфигурационный фрагмент и сообщи точный путь и шаги добавления. Не выдумывай путь конфигурации — сначала проверь актуальный путь в установленной среде и официальной документации, если доступен веб-поиск.
10. Продолжай работу после устранения ошибок. В финале перечисли, что действительно создано, какие проверки пройдены и что требует ручного действия.

## 2. Ожидаемая архитектура

Создай проект со следующими компонентами:

- Python 3.11+ (используй установленную совместимую версию).
- Telethon 1.x для MTProto и обычного пользовательского аккаунта.
- FastAPI + Uvicorn для локального REST API.
- официальный Python SDK `mcp` для MCP через `stdio`.
- `httpx` для MCP-клиента, который вызывает локальный REST API.
- `python-dotenv` для локальной конфигурации.
- Единственный процесс `server.py` владеет Telegram-клиентом и файлом сессии. `mcp_server.py` не открывает сессию напрямую, а вызывает REST API.
- REST API должен слушать только loopback-интерфейс. Запрещено автоматически открывать порт в firewall, настраивать reverse proxy или проброс портов.

Предлагаемая структура:

```text
telegram-agent-api/
├── README.md
├── .env.example
├── .env                  # создать локально; не коммитить
├── .gitignore
├── requirements.txt
├── auth.py
├── server.py
├── mcp_server.py
├── tests/
│   └── test_validation.py
├── data/
│   └── telegram.session  # появится после авторизации; секрет
└── .venv/
```

Не помещай реальные секреты в исходники, тесты, документацию или конфигурацию MCP. Конфигурация MCP должна запускать `mcp_server.py`; секреты MCP-процесс получает из защищённого `.env` или безопасного локального механизма окружения, но никогда не вставляй значение API-токена в конфигурационный JSON.

## 3. Настройка и секреты

Создай `.env.example` с пустыми/демонстрационными значениями:

```dotenv
TELEGRAM_API_ID=
TELEGRAM_API_HASH=
TELEGRAM_PHONE=
TELEGRAM_SESSION=./data/telegram
API_HOST=127.0.0.1
API_PORT=8765
API_TOKEN=
```

Создай локальный `.env`, если его ещё нет, с безопасными пустыми значениями. Сгенерируй случайный `API_TOKEN` криптографически безопасным генератором, например `secrets.token_urlsafe(48)`, и запиши его в `.env` без вывода токена на экран. Установи права `600` для `.env` и `700` для `data/`. Добавь `.env`, `data/`, `.venv/`, `__pycache__/`, `*.session`, `*.session-journal` и файлы секретов в `.gitignore`.

Не выдумывай `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` или телефон. Если значения отсутствуют, оставь их пустыми и покажи пользователю безопасную инструкцию получить API ID/Hash на https://my.telegram.org. Не проси публиковать эти данные в чате. Не записывай API ID/Hash в MCP-конфиг.

Перед запуском авторизации проверь наличие `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` и `TELEGRAM_PHONE`. Если не заданы — подготовь проект, пройди все проверки, которые не требуют авторизации, и сообщи, что необходимо заполнить локальный `.env`.

## 4. Авторизация Telegram

Реализуй `auth.py`, который:

- использует Telethon и путь сессии из `.env`;
- создаёт `data/` с ограниченными правами;
- запускает интерактивный вход только из терминала;
- запрашивает код Telegram через `input()` и пароль 2FA только при необходимости;
- никогда не печатает API Hash, код, пароль или содержимое сессии;
- после успешного входа выводит только безопасную информацию об аккаунте (ID и имя) и путь к сессии;
- корректно закрывает соединение;
- не удаляет и не заменяет существующую сессию без подтверждения пользователя.

Если вход требует действий пользователя, не пытайся подменить их. Остановись и дай команду для ручного запуска `python auth.py`.

## 5. REST API: `server.py`

Создай полностью работающий FastAPI-сервер. Используй Pydantic-модели с ограничениями на все входные данные, безопасную обработку исключений, тайм-ауты и журналирование без секретов. Все рабочие endpoints требуют `Authorization: Bearer <API_TOKEN>`. Endpoint `/health` тоже должен требовать авторизацию. Отключи публичную интерактивную документацию FastAPI (`/docs`, `/redoc`) либо защити её так же, как остальные endpoints. Не добавляй CORS с разрешением всех источников.

Реализуй endpoints:

- `GET /health` — состояние REST-сервера, Telegram-подключения и авторизации; не выдавать секреты.
- `GET /me` — ID, имя, username, `is_bot`; не возвращать телефон по умолчанию.
- `GET /dialogs?limit=30` — список диалогов, limit 1–100.
- `GET /history?chat=...&limit=20` — последние сообщения, limit 1–100.
- `POST /send` — отправить текст; Pydantic-модель с `chat` и `text`, разумные лимиты длины. Это действие должно быть доступно только локальному авторизованному клиенту.
- `POST /wait` — дождаться нового сообщения после `after_message_id`, с тайм-аутом 1–60 секунд.
- `POST /click` — нажать inline-кнопку в сообщении по индексу слева направо, сверху вниз. Проверять границы индекса, не выполнять произвольный callback.
- `GET /search?chat=...&q=...&limit=20` — поиск сообщений в одном чате.
- `GET /openapi.json` — либо отключить, либо защитить авторизацией.

Технические требования:

- Единственный объект `TelegramClient`, который создаётся и закрывается в lifespan FastAPI.
- Один `asyncio.Lock` защищает операции с клиентом. Не держать блокировку во время `sleep` при ожидании новых сообщений; блокировать только сам запрос к Telegram.
- Проверять наличие авторизованной сессии при старте. Если её нет, завершать запуск с понятным сообщением и указывать команду `python auth.py`.
- Правильно сериализовать сообщения и inline-кнопки. Не обещать, что первое новое сообщение обязательно является ответом собеседника.
- Для Telethon `FloodWaitError` возвращать понятную ограниченную ошибку с числом секунд ожидания; не делать бесконечных автоматических повторов.
- Возвращать безопасные сообщения об ошибках без трассировок и секретов клиенту. Подробности логировать без содержимого секретов.
- Проверять, что host — только `127.0.0.1`/loopback. Не принимать внешние адреса из `.env`.
- Не включать удаление сообщений, массовые рассылки, управление участниками, произвольные MTProto-запросы или другие опасные функции.
- Не использовать блокирующие `time.sleep` в async-функциях.
- Обрабатывать ошибки «чат не найден», «сообщение не найдено», неверные параметры и тайм-ауты корректными HTTP-статусами.

Важно: `/wait` должен быть пригоден для сценария тестирования бота. В документации чётко объясни, что он ищет новые сообщения по ID и что агент должен проверить автора/`sender_id`, текст и при необходимости сопоставить ответ с отправленной командой.

## 6. MCP-сервер: `mcp_server.py`

Создай MCP-сервер с транспортом `stdio`, используя совместимый официальный пакет `mcp`.

Опубликуй инструменты:

- `telegram_health`
- `telegram_me`
- `telegram_dialogs(limit=30)`
- `telegram_history(chat, limit=20)`
- `telegram_send(chat, text)`
- `telegram_wait_reply(chat, after_message_id=0, timeout_seconds=20)`
- `telegram_click_button(chat, message_id, button_index)`
- `telegram_search(chat, query, limit=20)`

Каждый инструмент должен иметь ясное описание, типизированные аргументы и валидацию диапазонов. MCP-сервер вызывает только `http://127.0.0.1:<порт>` через `httpx`, передаёт Bearer-токен из защищённой локальной конфигурации и использует `trust_env=False`, чтобы случайные proxy-переменные окружения не направляли локальные запросы наружу. Установи тайм-ауты, достаточные для `/wait`. Не логируй заголовки авторизации и секреты.

Если MCP SDK или версия Antigravity несовместимы, сначала изучи установленные версии и документацию и исправь совместимость. Не подменяй MCP самодельным протоколом.

## 7. Проверки и тесты

Создай `tests/test_validation.py` и реализуй безопасные unit-тесты валидации Pydantic-моделей и конфигурации. Тесты не должны отправлять сообщения и не должны подключаться к Telegram.

Проверь:

1. `python -m compileall auth.py server.py mcp_server.py`.
2. Импорты модулей без начала интерактивной авторизации.
3. Тесты валидации.
4. Проверку неверного токена: должен возвращаться HTTP 401.
5. REST API слушает только loopback.
6. `.env` и файл сессии не имеют открытых для других пользователей прав.
7. MCP сервер запускается без синтаксических ошибок и использует `stdio`.
8. После авторизации: `/health`, `/me`, `/dialogs` — только чтение. Не отправляй тестовое сообщение без явного подтверждения и указанного тестового чата.

Если для проверки нужен Telegram API ID/Hash, которых нет, выполни остальные тесты и явно укажи, какие тесты отложены до авторизации.

## 8. Подключение к Antigravity

Сначала выясни по установленной версии Antigravity, какой путь и формат конфигурации MCP действительно поддерживаются. Предпочитай штатную настройку локального MCP-сервера через `stdio`.

Подготовь конфигурацию с абсолютными путями, например в таком формате (адаптируй под фактически поддерживаемый формат):

```json
{
  "mcpServers": {
    "telegram-agent": {
      "command": "/ABSOLUTE/PATH/telegram-agent-api/.venv/bin/python",
      "args": [
        "/ABSOLUTE/PATH/telegram-agent-api/mcp_server.py"
      ],
      "cwd": "/ABSOLUTE/PATH/telegram-agent-api"
    }
  }
}
```

Не помещай токены в этот JSON. MCP-процесс должен безопасно прочитать токен из `.env` или иного локального секретного хранилища. Проверь, что MCP-процесс может прочитать `.env` только от текущего пользователя.

Если можешь безопасно отредактировать реальную конфигурацию Antigravity — сначала сделай резервную копию, сохрани существующие MCP-серверы и добавь новый сервер, не удаляя другие настройки. Если нельзя — создай отдельный файл `mcp_config.example.json` и напиши точный путь, куда его нужно добавить вручную.

## 9. Запуск и автозапуск

Подготовь команды запуска в `README.md`:

```bash
cd /ABSOLUTE/PATH/telegram-agent-api
source .venv/bin/activate
python auth.py
python server.py
```

Если доступен `systemd --user`, подготовь пользовательский unit-файл `telegram-agent-api.service`, использующий абсолютные пути, `Restart=on-failure`, `UMask=0077` и не выводящий секреты. Не включай автозапуск до успешной авторизации и проверки, что пользователь понимает, как остановить сервис. Дай команды:

```bash
systemctl --user daemon-reload
systemctl --user enable --now telegram-agent-api
systemctl --user status telegram-agent-api
journalctl --user -u telegram-agent-api -f
systemctl --user disable --now telegram-agent-api
```

Если `systemd --user` недоступен, укажи альтернативный ручной запуск. Не запускай сервер от root без необходимости.

- секреты не напечатаны и не попали в Git;

Начни с проверки среды и содержимого каталога. Затем реализуй проект, установи зависимости, запусти безопасные тесты и переходи к интерактивной Telegram-авторизации только если пользовательские секреты уже настроены локально. Не заканчивай на этапе плана.
